# SKILL.md — 모두의 외근 반복 작업 절차서

> 이 문서는 "어떻게 하는지"를 매번 새로 판단하지 않도록, 자주 반복되는 작업을 절차로 정리한 것이다.
> AGENTS.md의 규칙(폴더 구조·네이밍·에러 처리·디자인 토큰)을 전제로 한다. 새 절차가 생기면 이 문서에 계속 추가한다.

---

## 1. 새 화면(페이지) 추가하는 법

**언제 쓰나:** 주소 보정, 동선 추천처럼 새 서브 화면을 추가할 때.

1. 라우팅 폴더에 화면 폴더/파일 생성 (예: `/app/address` 또는 `/pages/address`)
2. 헤더·탭바는 새로 만들지 않고 기존 공통 레이아웃 컴포넌트를 그대로 불러와 쓴다.
   - 메인 탭 화면(홈/지도/고객/설정): 헤더에 워드마크 + 알림 아이콘, 하단 탭바 노출
   - 서브 화면(주소 보정/동선 추천): 헤더에 뒤로가기 + 화면 제목, 하단 탭바는 관련 메인 탭이 활성 상태로 유지 (Stitch 프롬프트 문서 기준: 주소보정→고객 탭 활성, 동선추천→홈 탭 활성)
3. 콘텐츠 영역 안에서만 화면별 컴포넌트를 새로 만든다. 헤더·탭바·카드·버튼 스타일은 절대 새로 만들지 않고 공통 컴포넌트를 재사용한다.
4. 데이터가 필요하면 2번(API 연동 패턴)을 따라 훅을 만든다.
5. 완료 후 AGENTS.md 8장 금지사항(매직 넘버, 복붙, absolute 배치)에 걸리는 게 없는지 스스로 점검한다.

---

## 2. API 연동 패턴 (프론트 → 백엔드)

**언제 쓰나:** 새 화면·기능이 백엔드 데이터를 불러오거나 보내야 할 때.

1. `/lib`(또는 `/services`)에 API 호출 함수를 만든다. 컴포넌트 안에서 직접 `fetch`를 호출하지 않는다.
2. 함수 이름은 동작을 그대로 드러내게 짓는다. 예: `getCustomerList()`, `updateCustomerStatus()`, `requestAddressCorrection()`
3. 커스텀 훅(`/hooks`)에서 이 함수를 호출하고, 로딩·에러·데이터 상태를 관리한다. 컴포넌트는 훅이 돌려주는 값만 받아서 화면을 그린다.
4. 에러가 나면 AGENTS.md 5장의 공통 에러 바운더리/토스트로 처리한다. 화면마다 새 에러 UI를 만들지 않는다.
5. 성공/실패 응답은 AGENTS.md 6장 포맷(`success`, `data` / `error`)을 그대로 기대한다. 다른 형태로 오면 백엔드 쪽부터 맞춘다.

## 3. 지도 핀 컴포넌트 사용/추가하는 법

**언제 쓰나:** 지도 화면, 홈 화면 미니맵, 동선 추천 화면처럼 핀이 필요한 모든 곳.

1. 핀 색상은 절대 직접 HEX 값을 넣지 않는다. 디자인 토큰의 상태별 색상(미컨택/컨택/완료/주소오류)을 가져와 쓴다.
2. **중복 주소 핀 규칙**을 반드시 지킨다: 같은 주소에 여러 건이 묶일 때, 미컨택이 하나라도 있으면 그 핀은 무조건 미컨택(빨강) 색으로 표시한다. (헛걸음 방지가 목적이므로 이 규칙은 임의로 바꾸지 않는다 — PRD 4-2)
3. 핀에 표시하는 정보는 "서비스 타입 + 모델명 + 고객 이름" 형식을 따른다.
4. 동선 추천 화면에서는 핀 위에 방문 순번(①②③…)을 추가로 표시하되, 핀 색 자체는 상태 색을 그대로 유지한다.
5. 핀 탭 시 뜨는 모달/바텀시트는 공통 컴포넌트 하나를 화면마다 재사용한다(지도/동선추천에서 다르게 새로 만들지 않는다).

---

## 4. 고객 상태 배지 다루는 법

**언제 쓰나:** 상태 배지(칩)를 새 화면에 추가하거나, 상태 관련 로직을 짤 때.

1. 상태의 내부 값은 AGENTS.md 3장 기준(`NOT_CONTACTED`, `CONTACTED`, `COMPLETED`, `ADDRESS_ERROR`)을 그대로 쓴다.
2. 화면에 보이는 이름(라벨)은 설정에서 사용자가 바꿀 수 있으므로, 내부 값과 화면 라벨을 분리해서 관리한다. 코드에 "미컨택"이라는 문자열을 직접 박지 않는다.
3. 배지 색은 상태별 디자인 토큰에서 가져온다. 배경은 해당 색의 15% 투명도, 글자는 해당 색 그대로(Stitch 프롬프트 문서 기준).
4. 새로운 상태를 추가하는 건 기획 변경 사항이다. 임의로 상태를 늘리지 말고 먼저 사람에게 확인한다.

---

## 5. 디자인 토큰 추가/수정하는 법

**언제 쓰나:** 새로운 색상·간격·폰트 크기가 필요할 때, 또는 Stitch 디자인 결과를 코드에 반영할 때.

1. 화면 코드에 값을 직접 쓰지 않는다. 먼저 디자인 토큰 파일(`/design-tokens`)에 값을 추가한다.
2. 이미 비슷한 토큰이 있는지 먼저 확인한다 (예: 간격은 `4,8,12,16,24,32,40`px 중에서만 고른다).
3. 상태 색(미컨택/컨택/완료/주소오류)처럼 PRD에 고정된 값은 함부로 수치를 바꾸지 않는다. 톤만 미세 조정이 필요하면 사람에게 먼저 확인한다.
4. 토큰을 바꾼 뒤에는, 그 토큰을 쓰는 화면들이 의도대로 다 같이 바뀌는지 확인한다 (한 곳만 고치고 끝내지 않는다).

## 6. 새 에러 코드 추가하는 법

**언제 쓰나:** 백엔드에서 새로운 실패 상황(예: 주소 보정 API 타임아웃)을 처리해야 할 때.

1. 에러 코드는 `대문자_스네이크` 형식으로, 무엇이 실패했는지 이름만 봐도 알 수 있게 짓는다. 예: `ADDRESS_GEOCODE_FAILED`, `ROUTE_API_TIMEOUT`
2. 전역 예외 처리 한 곳에서 AGENTS.md 5장 포맷으로 응답한다. 컨트롤러마다 따로 처리하지 않는다.
3. AX 기능(주소 보정, 동선 최적화) 관련 에러는 반드시 Fallback을 함께 정의한다 (예: 동선 API 실패 → 단순 거리순 정렬). "에러만 던지고 끝"은 AX 기능에서 허용하지 않는다.
4. 에러를 추가한 뒤, 그 에러가 났을 때 화면에 사람이 어떤 메시지를 보게 되는지 한 문장으로 확인한다.

## 7. AX 기능 붙일 때 체크리스트

**언제 쓰나:** 주소 보정, 동선 최적화 등 AI/외부 API가 들어가는 기능을 만들 때.

- [ ] 이 기능이 실패해도 DX 핵심 기능(핀 보기·상태 관리·전화·네비)은 정상 동작하는가?
- [ ] "자동으로 다 처리"가 아니라 "후보 제안 + 신뢰도가 낮으면 확인 요청" 구조로 되어 있는가? (PRD 5장 설계 철학)
- [ ] 실패 시 Fallback이 정의되어 있는가? (AGENTS.md 5장)
- [ ] 이 기능은 비용이 드는 외부 API(지오코딩·LLM)를 호출하므로, 호출량이 과도하게 늘어나지 않는 구조인가?
- [ ] 성공 지표(채택률, 정확도 등)를 나중에 측정할 수 있는 데이터가 남는가?

## 8. Git 작업 절차 (브랜치 생성 → 커밋 → PR)

**언제 쓰나:** 새 기능이나 수정 작업을 시작할 때부터 끝낼 때까지.

1. 작업 시작 전, 프로젝트 최상위 폴더에서 `main`을 최신으로 맞춘다.
   ```bash
   git checkout main
   git pull origin main
   ```
2. AGENTS.md 4-2 규칙에 맞는 이름으로 브랜치를 만들고 이동한다.
   ```bash
   git checkout -b feature/fe-login
   ```
   - 프론트: `feature/fe-...` / 백엔드: `feature/be-...` / 버그 수정: `fix/fe-...`, `fix/be-...`
3. 작업은 하나의 커밋이 하나의 작업 단위가 되도록 나눈다 (기능 하나, 수정 하나).
4. 커밋 전, `.env` 등 비밀 파일이 포함되지 않았는지 확인한다 (AGENTS.md 11장).
5. AGENTS.md 4-4 컨벤션(`타입: 설명`)으로 커밋한다.
   ```bash
   git add .
   git commit -m "feat: 지도 핀 클릭 시 상태 변경 모달 추가"
   ```
6. 브랜치를 원격 저장소에 올리고 PR을 만든다.
   ```bash
   git push origin feature/fe-login
   ```
   - GitHub에서 `main`으로 PR 생성, 무엇을 했는지 간단히 작성
7. 병합 후에는 로컬·원격 브랜치를 모두 정리한다.
   ```bash
   git branch -d feature/fe-login
   git push origin --delete feature/fe-login
   ```
8. 마무리 후 사람에게 "무엇을 바꿨는지 / 왜 / 확인할 부분"을 짧게 요약해 전달한다 (AGENTS.md 1장).
