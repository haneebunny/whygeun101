## 1. 사람과의 소통 방식 (최우선)

이 프로젝트를 함께하는 사람은 다음 조건을 갖고 있다. 모든 답변·설명은 이 조건에 맞춰야 한다.

- 예전에 프론트엔드를 배웠지만 지금은 직접 코드를 작성하는 능력이 거의 없다. **코드는 Claude가 작성하고, 사람은 읽고 판단**하는 역할이다.
- **비전공자**다. 어려운 개발 용어를 쓰지 않는다. 꼭 필요한 용어는 한 줄로 쉽게 풀어서 설명한다.
- **Java를 거의 모른다.** 백엔드를 바꿀 때는 특히 더 친절하게, 무엇을 왜 했는지 일상어로 요약한다.
- PM·AX/DX 엔지니어를 지망한다. 코드 자체보다 **"왜 이렇게 결정했는지(기획 의도·트레이드오프)"**를 함께 설명한다. 이 설명은 나중에 포트폴리오 스토리로 쓰인다.

**변경할 때마다 다음 세 가지를 짧게 정리한다.**
1. 무엇을 바꿨는지
2. 왜 그렇게 했는지
3. 사람이 확인하거나 결정해야 할 부분

**작업 태도**
- 큰 변경은 한 번에 쏟아내지 않는다. 먼저 계획을 짧게 보여주고 확인받은 뒤 진행한다.
- 모르거나 모호한 부분은 추측하지 말고 질문한다.
- 기획·제품 관점에서 의미 있는 결정(예: AX 기능 설계)은 그 이유를 문서나 커밋 설명에 남긴다.

## 2. 폴더 구조 (실제 구조)

> 현재 프로젝트는 Next.js App Router와 Clean Architecture 계층 구조가 혼용되어 사용되고 있습니다.

**프론트엔드 (Next.js)**
```
/app                      Next.js App Router 라우팅 (페이지 단위: 홈, 인증, 개인정보 등)
/components               공통 UI 컴포넌트
/src                      비즈니스 로직 및 세부 컴포넌트 레이어
  /data                   데이터 소스 및 API 연동
  /domain                 비즈니스 모델 및 규칙
  /presentation           화면 표시 관련 요소
    /components           프레젠테이션용 공통 컴포넌트
    /features             화면별 세부 기능 컴포넌트
```

**백엔드 (Spring Boot)**
```
/src/main/java/...
  /controller             요청을 받는 곳 (API 입구, "무엇을 받을지"만 담당)
  /service                실제 로직 (판단·계산은 여기서)
  /repository             DB 접근
  /dto                    주고받는 데이터 형태 정의
  /domain (entity)        DB 테이블과 연결된 데이터 구조
  /exception              에러 정의 및 공통 처리
  /config                 환경설정, 보안 설정
```

## 3. 네이밍 규칙

- 컴포넌트 파일: PascalCase (예: `CustomerCard.tsx`)
- 함수·변수: camelCase
- 상수: UPPER_SNAKE_CASE
- **고객 상태값은 아래 값으로 통일**한다 (PRD 2장 기준, 화면 표시 이름은 설정에서 바뀌어도 내부 값은 고정):
  - 미컨택 → `NOT_CONTACTED`
  - 컨택 → `CONTACTED`
  - 완료 → `COMPLETED`
  - 주소 오류 → `ADDRESS_ERROR`

## 4. Git 브랜치 전략 및 커밋 규칙

> **[절대 규칙]** 사소한 문서 수정(README, 가이드라인 등) 및 긴급 패치(hotfix)를 포함한 **모든 작업은 예외 없이 별도의 독립된 브랜치를 파서 진행**해야 하며, `main` 브랜치에 직접 커밋하거나 push하는 행위는 어떠한 경우에도 금지합니다. 모든 코드는 Pull Request(PR)를 통한 병합으로만 `main`에 반영되어야 합니다.

### 4-1. 브랜치 종류

| 브랜치 | 용도 |
|---|---|
| `main` | 프로덕션 배포 및 최종 완성본. **직접 커밋/Push 절대 금지** |
| `feature/...` | 기능 개발용 독립 브랜치 |
| `fix/...` | 버그 수정 및 문서/기타 패치용 독립 브랜치 |

### 4-2. 브랜치 이름 짓기

형태: `접두어/파트-작업내용` (소문자, 단어 구분은 하이픈 `-`)

| 상황 | 예시 |
|---|---|
| 프론트엔드 기능 개발 | `feature/fe-login`, `feature/fe-main-page` |
| 백엔드 기능 개발 | `feature/be-matching-api`, `feature/be-db-setup` |
| 프론트 버그 수정 | `fix/fe-버그명` |
| 백엔드 버그 수정 | `fix/be-버그명` |

### 4-3. 작업 시작 절차 (항상 최신 main에서 시작)

프로젝트 최상위 폴더에서 실행한다 (본인 파트 폴더 아님).

```bash
# 1. main 브랜치로 이동
git checkout main
# 2. 원격 저장소의 최신 코드 동기화
git pull origin main
# 3. 새 기능 브랜치를 만들고 동시에 이동
git checkout -b feature/fe-login
```

- 지금 어느 브랜치에 있는지 확인: `git branch` (초록색으로 현재 브랜치 표시)

### 4-4. 커밋 컨벤션

`타입: 설명` 형태로 작성한다 (한글 작성 가능). 제목만 봐도 무슨 변화인지 알 수 있게 쓴다.

| 타입 | 의미 |
|---|---|
| `feat` | 새 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 (README, 가이드라인 등) |
| `style` | 코드 포맷팅, 세미콜론 누락 등 (로직 변경 없음) |
| `refactor` | 기능 추가·버그 수정 없이 코드 구조만 개선 |
| `chore` | 빌드 업무, 패키지 매니저 설정, `.gitignore` 수정 등 |

예시
```
feat: 지도 핀 클릭 시 상태 변경 모달 추가
fix: 백엔드 매칭 API 데이터 포맷 에러 수정
docs: README.md에 프로젝트 소개 문구 추가
chore: .gitignore에 node_modules 및 .next 경로 추가
```

### 4-5. 작업 마무리 — Push & PR

1. 변경 사항 확인 후 커밋
   ```bash
   git add .
   git commit -m "feat: 지도 핀 클릭 시 상태 변경 모달 추가"
   ```
2. 원격 저장소에 브랜치 올리기
   ```bash
   git push origin feature/fe-login
   ```
3. GitHub에서 `feature/fe-login` → `main`으로 PR(Pull Request) 생성
   - PR 제목·설명에 "무엇을 했는지"를 커밋 메시지와 비슷한 수준으로 간단히 적는다
4. 리뷰(또는 최소한의 확인) 후 `main`에 병합(Merge)
5. 병합이 끝난 브랜치는 삭제한다 (로컬·원격 모두)
   ```bash
   git branch -d feature/fe-login
   git push origin --delete feature/fe-login
   ```

> **주의:** `.env` 등 비밀 파일은 커밋 전에 반드시 확인한다 (11장 참고). 실수로 push까지 됐다면 즉시 알린다.

## 5. 에러 핸들링 규약 (백/프론트 공통)

> 지금까지는 에러가 나면 그냥 터지거나 화면마다 다르게 처리되어 왔다. 앞으로는 아래 형태 하나로 통일한다.

**백엔드 표준 에러 응답**
```json
{
  "code": "ADDRESS_GEOCODE_FAILED",
  "message": "주소를 좌표로 변환하지 못했습니다.",
  "detail": "부가 설명 (선택)"
}
```
- 모든 예외는 전역 예외 처리 한 곳(예: `@ControllerAdvice`)에서 이 형태로 변환해 내려준다. 컨트롤러 하나하나에서 따로 에러 형태를 만들지 않는다.

**프론트엔드**
- 공통 에러 바운더리 + 공통 토스트(알림) 컴포넌트 하나로 모든 API 에러를 처리한다. 화면마다 각자 에러 문구·UI를 새로 만들지 않는다.
- 로딩·재시도 상태도 공통 패턴을 만들어 재사용한다.

**AX 기능(주소 보정, 동선 최적화) 관련 원칙**
- AX 기능이 실패해도 DX 핵심 기능(핀 보기, 상태 관리, 전화, 네비)은 절대 멈추면 안 된다.
- 지오코딩 실패 시: 원본 주소 유지 + "보정 실패" 표시 + 주소 오류 목록에 보관
- 동선 API 실패 시: 단순 거리순 정렬로 대체
- (전략기획서 4-3 Fallback 전략과 동일하게 유지)

## 8. 금지사항

- `.env` 등 비밀 파일을 git에 커밋하는 것 (6장 참고, 절대 규칙)
- 코드에 값을 직접 박아 넣는 것(매직 넘버) — 반드시 설정/디자인 토큰으로 분리
- 같은 스타일·로직 코드를 여러 화면에 복사 붙여넣기 — 공통 컴포넌트/함수로 분리
- `margin`, `position: absolute`, 고정 `px` 값으로 레이아웃을 잡는 것 — flex + gap으로 해결 (9장 참고)
- 고객 상태의 색상-의미 매핑(미컨택=빨강 계열, 컨택=노랑 계열, 완료=파랑 계열, 주소오류=회색 계열)을 임의로 바꾸는 것 — PRD 2장 기준 고정

## 9. 프론트엔드 규칙

- 레이아웃은 **flex와 gap 위주**로 짠다. `margin`, `position: absolute`, 고정 `px` 값으로 정렬·간격을 잡지 않는다.
- 간격 값은 디자인 토큰의 간격 스케일에서 가져온다. 직접 숫자를 쓰지 않는다.
  - 스케일 기준(Stitch 프롬프트 문서 기준): `4, 8, 12, 16, 24, 32, 40px`
- 색상·폰트·radius 등은 모두 디자인 토큰에서 가져온다. (Stitch 프롬프트 문서의 "공통 디자인 시스템" 표가 토큰의 기준값)
- 모바일 우선으로 만들되, 웹뷰 앱 전환을 고려한다 (하단 탭바, `safe-area` 여백).
- 글라스모피즘 적용 시 점검할 것:
  - 반투명 배경 위 텍스트는 항상 충분한 대비를 유지 (불투명한 짙은 텍스트 색 사용)
  - `backdrop-filter: blur()`는 헤더·탭바·카드 등 제한된 영역에만 사용 (모바일 성능 부담)
  - 배경이 단조로우면 효과가 살지 않으므로 은은한 그라데이션 배경과 함께 사용

## 10. 백엔드 규칙

- 사람이 Java를 거의 모르므로, 백엔드를 바꿀 때는 반드시 평소 말로 무엇을 했는지 요약한다 (1장 참고).
- 에러 처리는 5장 규약을 따른다. 에러가 그냥 터지게 두지 않는다.
- 비밀값(키, 비밀번호, 토큰)은 코드에 직접 쓰지 않고 환경변수로 다룬다 (11장 참고).

---

## 11. 보안 / Git (절대 규칙)

- `.env`, `.env.*` 같은 환경설정·비밀 파일은 절대로 git에 올리지 않는다.
- `.gitignore`에 `.env*`가 포함되어 있는지 항상 확인한다. 이미 올라가 있다면 즉시 알리고 제거 절차를 안내한다.
- API 키, 비밀번호, 토큰을 코드나 커밋 메시지에 노출하지 않는다.
- 비밀값이 노출될 위험이 의심되면, 커밋하기 전에 먼저 사람에게 물어본다.

---

## 12. 클린 코드 원칙 (요약)

- 역할별로 파일·폴더를 나눈다. 화면 그리는 코드 / 로직 / 데이터 불러오는 코드를 한 파일에 섞지 않는다.
- 함수는 한 가지 일만 하고, 이름만 봐도 무슨 일을 하는지 알 수 있게 짓는다.
- 같은 코드를 여러 곳에 복사해 붙이지 않는다. 공통 부분은 한 곳에 모은다.
- 주석은 "왜 이렇게 했는지"가 코드만 봐서는 안 드러나는 곳에만 단다. 뻔한 내용에는 달지 않는다. 이모지는 쓰지 않는다.
